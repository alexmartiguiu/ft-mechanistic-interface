# FTMI — API One-Pager (for Frontend Design)

**What this is:** `ftmi` is a fine-tuning harness that mints "concept vectors", fine-tunes a
model with LoRA while monitoring concept drift, evaluates each checkpoint, and builds a report.

**⚠️ Read this first — there is no web API yet.** The application is a **command-line tool +
Python library** that reads YAML config files and writes result files to disk. There is **no
HTTP/REST server, no websocket, no job/status endpoint**. The `webui/` directory is empty. To
build a frontend against this, someone must first write a thin HTTP layer that (a) launches CLI
commands as jobs, (b) reports their progress, and (c) serves the result files. This doc describes
the surface that layer would wrap, plus the data shapes the UI will render.

---

## 1. The operations (today: CLI commands)

These are the actions a UI would trigger. Each is a long-running job (minutes to hours), so the
UI model is **submit job → poll status → render artifacts**, not request/response.

| Operation | Command | What it does | Duration |
|---|---|---|---|
| Mint vectors | `ftmi vectors --concepts <yaml> --model <id>` | Build + validate concept vectors | ~minutes |
| Train | `ftmi train --app <yaml>` | LoRA fine-tune with drift monitoring | minutes–hours |
| Evaluate | `ftmi eval --app <yaml>` | Per-checkpoint benchmark battery | minutes–hours |
| **Run end-to-end** | `ftmi run --app <yaml>` | vectors → train → eval → report (pipelined) | hours |
| Propose concepts | `ftmi concepts ...` | Auto-suggest concepts from a dataset | — (**NOT IMPLEMENTED**, stub) |

`ftmi run` is the primary entry point — it orchestrates everything and is what most UI flows
should call. Useful flags: `--model` (swap model family), `--name` (output namespace),
`--train-gpu` / `--eval-gpu` (pin GPUs; if different, eval runs concurrently with training),
`--skip-vectors`, `--skip-eval`, `--skip-report`, `--max-samples` (smoke test).

## 2. The inputs (config files the UI would author/edit)

A UI's main editing surface. Three linked YAML files:

**Application config** (`configs/applications/*.yaml`) — the top-level job spec:
```yaml
name: therapist
lora: configs/lora/qwen7b_default.yaml     # -> LoRA recipe
concepts: configs/concepts/therapist.yaml  # -> concept set
data: { path, text_field, valid_fraction, max_seq_len }
monitor:  { enabled, layer }               # drift monitoring
audit:    { enabled, flag_percentile }     # pre-train data audit
mitigate: { mode: none|steer|suppress, coef }
eval:     { mmlu_pro, truthfulqa, safety{...}, vllm{...} }
```

**Concept set** (`configs/concepts/*.yaml`) — the safety axes to track:
```yaml
domain: therapist
concepts:
  - { name: crisis_minimization, description: "<one paragraph>" }
  - ...
```

**LoRA recipe** (`configs/lora/*.yaml`) — training hyperparameters:
```yaml
model_id: Qwen/Qwen2.5-7B-Instruct
dtype: bfloat16
lora:  { r, alpha, dropout, target_modules: [...] }   # target_modules differ per model family
optim: { lr, epochs, batch_size, grad_accum, warmup_ratio, max_seq_len }
checkpoint: { save_every_steps, n_checkpoints, monitor_every_steps, log_every_steps, keep_last }
```

## 3. The outputs (files the UI would read & visualize)

Everything lands under `data/<name>/`. These JSON files are the de-facto "response payloads":

- `data/<name>/vectors/<concept>.json` — per-concept: layer, probe AUROC, n_pos/n_neg,
  validation report (dose-response grid). *(plus `.npz` weight files the UI won't read)*
- `data/<name>/checkpoints/train_summary.json` — **drift trajectory** (projection + probe
  probability per concept over training steps), audit + mitigation results. The headline chart.
- `data/<name>/checkpoints/checkpoint-*/trainer_state.json` — train/eval loss per step.
- `data/<name>/results/<tag>/*_summary.json` — eval battery per checkpoint (`base`, `final`,
  `checkpoint-N`): MMLU-Pro accuracy, TruthfulQA accuracy, HarmBench/StrongREJECT refusal rates.
- `data/<name>/results/summary.json` — assembled base→final comparison.

There is also an **HTML report** generated by `scripts/build_report.py` (self-contained, inline
SVG charts) — useful as a reference for exactly what the UI should visualize (loss curves, drift
trajectories, eval deltas).

## 4. Programmatic Python API (if the frontend backend is Python)

If the HTTP wrapper is written in Python, it can import these instead of shelling out to the CLI:

- `ftmi.config` — `ApplicationConfig.load(path)`, `ConceptSet.load(path)`, `LoraConfig.load(path)`,
  `.with_overrides(model, name, lora_config)`. Typed, frozen dataclasses — good for validation.
- `ftmi.run.run_e2e(...)` — the full pipeline.
- `ftmi.eval.harness.run_eval(cfg, ...)`, `ftmi.train.lora.train_lora(...)`,
  `ftmi.vectors.pipeline.mint_vector(...)` — individual stages.
- `ftmi.eval.common.list_checkpoints(app)` — enumerate checkpoints/tags for a run.
- `ftmi.schemas` — Pydantic models (`ArtifactsOut`, `ConceptOut`, `JudgeScore`) usable directly
  as API response/validation schemas.

Backends needed: `ANTHROPIC_API_KEY` or `GEMINI_API_KEY` (artifact generation + judging),
optional `HF_TOKEN`, and GPU pinning via `CUDA_VISIBLE_DEVICES`.

---

## 5. Completeness — what's solid vs. what needs work

**Solid / production-ready:** config system, vector pipeline, training + drift monitor, eval
harness (phased + resumable), `ftmi run` orchestration, the HTML report. All stages are
file-based and resumable, which is friendly to a poll-based UI.

**Gaps / best-effort — flag these to the team before designing:**

1. **No HTTP/API layer at all (biggest gap).** This is the prerequisite for any frontend. Needs:
   job submission, **job status/progress** (currently progress is only inferable by watching files
   appear on disk), result retrieval, and config CRUD/validation. Recommend a small FastAPI
   service wrapping `ftmi.run` + the config dataclasses.
2. **No streaming/live progress.** Training/eval emit logs and W&B metrics, but nothing the UI can
   subscribe to. A live drift-trajectory or loss view would need a tail/websocket endpoint built.
3. **`ftmi concepts` is a stub** — raises "not yet implemented". If the UI offers
   "auto-suggest concepts from my dataset," that feature doesn't exist yet (the underlying
   `propose_concepts()` function does, but it isn't wired to the CLI).
4. **No auth / multi-user / run registry.** Runs are just directories under `data/`; there's no
   index, ownership, or listing endpoint. A "list my runs" view needs that built.
5. **Outputs are a file convention, not a versioned schema.** Fine for internal use, but the JSON
   shapes aren't formally contracted — pin them down before the UI hardcodes field names.

---

*Bottom line for the designer: design around the **submit → poll → visualize** model. The data
model (configs in, drift + eval JSON out) is real and stable; the network API that exposes it is
the missing piece that needs to be built first.*
